# Документна модель MongoDB (ActivitiesDb)

## 1. Контекст та архітектурне призначення
У розподіленій CRM-системі для веб-студії та digital-маркетингу (3–10 осіб) сервіс **Комунікації та активності** використовує NoSQL базу даних **MongoDB 8.0**. 

На відміну від реляційних даних з фіксованою структурою (каталог послуг, бухгалтерські транзакції), комунікації з клієнтами мають високу варіативність:
- Різні типи взаємодій містять принципово різні атрибути (дзвінки мають тривалість і напрямок, зустрічі — локацію та порядок денний, листи — тему та вкладення).
- Швидкість додавання нотаток та фіксації результатів комунікацій критична для продуктивності менеджерів.
- Потрібна підтримка повнотекстового пошуку по примітках, швидка побудова стрічки подій (timeline) та горизонтальне масштабування при зростанні обсягів листування.

## 2. Стратегії моделювання даних

### 2.1. Гнучка поліморфна схема (Flexible Schema) — Колекція `activities`
Колекція `activities` об'єднує всі види взаємодій під єдиним поліморфним коренем. Спільні поля та специфічні атрибути валідуються на рівні колекції через `$jsonSchema` (зі значенням `validationAction: "error"`, що відхиляє невалідні документи, зокрема тип `fax`):

- **Спільні обов'язкові поля**:
  - `_id`: унікальний BSON ObjectId.
  - `type`: один із дозволених типів `['call', 'email', 'meeting', 'note', 'task']`.
  - `clientId`: ідентифікатор клієнта (числовий `NumberLong`, відповідає `Clients.Id` у `SalesDb`).
  - `clientName`: денормалізована назва контрагента для швидкого відображення без міжсервісних запитів.
  - `author`: вбудований документ `{ userId, displayName }`.
  - `createdAt`: дата і час події (ISODate).
  - `dealId` та `dealTitle` (опціонально): прив'язка до конкретної угоди у воронці продажів.
- **Поліморфні поля за типами**:
  - `call`: `direction` (`inbound` / `outbound`), `durationSec` (тривалість у секундах), `outcome` (результат).
  - `email`: `subject` (тема листа), `attachments` (масив імен прикріплених файлів).
  - `meeting`: `location` (Google Meet, Zoom або офлайн-адреса), `participants` (масив учасників), `agenda` (порядок денний).
  - `note`: `text` (текстовий опис/нотатка без додаткових метаданих).
  - `task`: `dueDate` (дедлайн), `done` (булевий статус виконання).

### 2.2. Вбудовування (Embedding)
- **Коментарі (`comments`) в `activities`**:
  Коментарі колег (наприклад, коментар арт-директора до дзвінка менеджера) вбудовуються безпосередньо в документ активності у вигляді масиву `comments: [{ author, text, createdAt }]`. Оскільки кількість коментарів до однієї активності обмежена (зазвичай 1–5), це забезпечує атомарність оновлення через оператор `$push` і читання всієї картки за 1 операцію.
- **Автор (`author`) та пов'язані продукти (`relatedProducts`)**:
  Вбудовані піддокументи дозволяють миттєво відображати ім'я менеджера та назви послуг з прайс-листа без потреби додаткових запитів до `SalesDb` чи `CatalogDb`.

### 2.3. Посилання (Referencing) — Колекції `discussions` та `discussion_messages`
- **Чому повідомлення відокремлені від теми обговорення?**
  У проектних обговореннях веб-студії (наприклад, затвердження дизайну чи технічного завдання) кількість реплік може сягати сотень і тисяч.
  1. **Ліміт BSON-документа 16 МБ**: Вбудовування необмеженого масиву повідомлень у документ теми рано чи пізно призведе до перевищення ліміту `16MB Document Size Limit`.
  2. **Продуктивність пам'яті (RAM / Working Set)**: Завантаження всієї теми з 2000 повідомлень заради перевірки статусу створює надмірне навантаження на I/O та пам'ять.
  3. **Пагінація та конкурентність**: Окрема колекція `discussion_messages` дозволяє виконувати ефективну пагінацію (`.find().sort({ createdAt: 1 }).skip().limit()`) та паралельний запис повідомлень різними користувачами без блокування всього документа теми.

### 2.4. Гібридний підхід (Subset / Hybrid Pattern) — Колекція `client_timelines`
Картка клієнта в CRM вимагає миттєвого рендерингу останніх 5 подій без виконання важких агрегацій по всій базі `activities`.
- У `client_timelines` зберігається документ з денормалізованим масивом останніх 5 активностей:
  ```json
  {
    "clientId": 1,
    "activityCount": 18,
    "recentActivities": [
      { "activityId": ObjectId(...), "type": "call", "createdAt": ISODate(...), "summary": "..." },
      ...
    ]
  }
  ```
- При додаванні нової активності таймлайн оновлюється однією атомарною операцією:
  ```javascript
  db.client_timelines.updateOne(
    { clientId: 1 },
    {
      $inc: { activityCount: 1 },
      $push: {
        recentActivities: {
          $each: [{ activityId: newId, type: "call", createdAt: new Date(), summary: "..." }],
          $sort: { createdAt: -1 },
          $slice: 5
        }
      },
      $set: { updatedAt: new Date() }
    },
    { upsert: true }
  );
  ```
- Якщо менеджер натискає «Переглянути всю історію», застосунок робить запит за посиланням у колекцію `activities`.

## 3. Стратегія індексації

| Колекція | Поля індексу | Тип індексу | Призначення / Під який запит створено |
| :--- | :--- | :--- | :--- |
| `activities` | `{ clientId: 1, createdAt: -1 }` | Compound | Вибірка повної стрічки комунікацій клієнта від найновіших |
| `activities` | `{ dealId: 1 }` | Single field | Фільтрація історії взаємодій за конкретною угодою воронки |
| `activities` | `{ "author.userId": 1 }` | Single field | Розрахунок щоденної активності та KPI конкретного менеджера |
| `activities` | `{ type: 1 }` | Single field | Фільтрація стрічки за типом (лише дзвінки, лише зустрічі) |
| `activities` | `{ text: "text", clientName: "text" }` | Text | Повнотекстовий пошук по нотатках, темах листів та клієнтах |
| `discussions` | `{ clientId: 1, createdAt: -1 }` | Compound | Список відкритих/архівних тем обговорень контрагента |
| `discussions` | `{ dealId: 1 }` | Single field | Список обговорень у межах поточної угоди |
| `discussion_messages` | `{ discussionId: 1, createdAt: 1 }` | Compound | Хронологічний вивід повідомлень гілки з підтримкою пагінації |
| `client_timelines` | `{ clientId: 1 }` | Unique | Миттєвий пошук O(1) віджета таймлайну та запобігання дублікатів |

## 4. Приклади Aggregation Pipelines

В `queries.js` реалізовано три ключові аналітичні конвеєри агрегації:
1. **Підрахунок кількості активностей за типами**: `$group` за `$type` з підрахунком `$sum: 1` для аналітики завантаженості каналів зв'язку.
2. **Найактивніші клієнти за останні 30 днів**: `$match` за діапазоном дат, `$group` по `$clientId`, сортування за спаданням кількості подій, `$limit: 5`.
3. **Середня тривалість дзвінків по співробітниках**: `$match: { type: "call" }`, `$group` за `author.displayName` із розрахунком `$avg: "$durationSec"`.
