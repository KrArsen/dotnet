# Опис предметної області та Bounded Contexts (CRM для малого бізнесу)

## 1. Короткий опис домену (Domain Summary)
Система є спеціалізованою CRM для студії веб-розробки та цифрового маркетингу зі штатом 3–10 співробітників (власник студії та менеджери з продажів). Вона забезпечує централізований облік корпоративних клієнтів, супровід угод через етапи воронки продажів, управління каталогом послуг і супутніх цифрових товарів, а також фіксацію повної хронології комунікацій (дзвінки, листування, зустрічі, нотатки та задачі). Завдяки декомпозиції на мікросервісні контексти студія отримує високу автономність процесів продажів, ціноутворення та клієнтської підтримки.

---

## 2. Bounded Contexts та архітектурне розділення

Система декомпозована на три незалежні контексти (Bounded Contexts) відповідно до патерну **Database per Service**:

```
+----------------------------------------------------------------------------------------------------+
|                                    CRM ДЛЯ МАЛОГО БІЗНЕСУ                                          |
+----------------------------------------------------------------------------------------------------+
       |                                          |                                           |
       v                                          v                                           v
+-----------------------------+     +-----------------------------+     +----------------------------+
|      Sales Context          |     |      Catalog Context        |     |     Activities Context     |
|   (Контекст «Продажі»)      |     |   (Контекст «Прайс-лист»)   |     | (Контекст «Комунікації»)   |
+-----------------------------+     +-----------------------------+     +----------------------------+
| СУБД: MS SQL Server 2022    |     | СУБД: MS SQL Server 2022    |     | СУБД: MongoDB 8.0          |
| База: SalesDb               |     | База: CatalogDb             |     | База: ActivitiesDb         |
| Стек: ADO.NET + Dapper      |     | Стек: EF Core Code First    |     | Стек: MongoDB Driver       |
| Орієнтація: високий TPS,    |     | Орієнтація: каталог, зв'язки|     | Орієнтація: гнучка схема,  |
| строгі транзакції, черги    |     | послуг, історія тарифів     |     | поліморфні події, таймлайн |
+-----------------------------+     +-----------------------------+     +----------------------------+
```

### 2.1. Контекст «Продажі» (SalesDb)
- **Відповідальність:** Управління співробітниками відділу продажів (`TeamMembers`), ведення контрагентів (`Clients`), оформлення угод (`Deals`) через воронку продажів (`Lead` → `Qualified` → `ProposalSent` → `Negotiation` → `Won` / `Lost`), фіксація позицій угод (`DealItems`) із незмінними знімками цін та журналу переходу статусів (`DealStatusHistory`).
- **Стек:** Dapper та ADO.NET. Пряме управління транзакціями та рівнем блокувань (`UPDLOCK, ROWLOCK`) гарантує неможливість колізій при паралельному русі угод по воронці кількома менеджерами.
- **Власні сутності:** `TeamMembers`, `Clients`, `Deals`, `DealDetails`, `DealItems`, `DealStatusHistory`.
- **Локальна проекція:** Таблиця `Products` (локальна репліка прайс-листа без міжсерверного зовнішнього ключа, оновлюється доменними подіями з каталогу).

### 2.2. Контекст «Прайс-лист» (CatalogDb)
- **Відповідальність:** Управління номенклатурою цифрових послуг та товарів веб-студії (розробка лендінгів, корпоративних сайтів, SEO-аудити, SMM, хостинг, ліцензії), категоризація, облік одиниць виміру та тривалості робіт, а також зберігання історії змін тарифів.
- **Стек:** Entity Framework Core Code First. Чітка типізація, навігаційні властивості та підтримка міграцій.
- **Власні сутності:** `Product`, `ProductDetail`, `PriceHistory`, `Category`, `ProductCategory`.

### 2.3. Контекст «Комунікації та активності» (ActivitiesDb)
- **Відповідальність:** Збір і відображення повної історії взаємодій із клієнтами та по конкретних угодах: телефонні дзвінки, email-листування, офлайн/онлайн зустрічі, робочі нотатки та задачі. Також веде тематичні гілки обговорень і агреговані таймлайни активності клієнта.
- **Стек:** MongoDB 8.0. Поліморфна документоорієнтована модель із суворою `$jsonSchema`-перевіркою та гібридною структурою (вбудовані коментарі та останні 5 знімків активностей у таймлайні, винесені повідомлення для довгих обговорень).
- **Колекції:** `activities`, `discussions`, `discussion_messages`, `client_timelines`.

## 3. Опис агрегатів (Aggregates)

Відповідно до тактичних патернів DDD, межі транзакційної узгодженості проходять по агрегатах:

1. **Агрегат «Угода» (Deal Aggregate) — у SalesDb:**
   - **Корінь агрегату (Aggregate Root):** Таблиця `Deals`.
   - **Внутрішні сутності:** `DealDetails` (зв'язок 1:1, містить джерело ліда, розширений опис, причину програшу `LostReason` та очікувану дату закриття) та `DealItems` (зв'язок 1:N, позиції угоди зі знімками назви й ціни).
   - **Журнал агрегату:** `DealStatusHistory` (фіксує кожен перехід по воронці).
   - **Правило інваріанта:** Каскадне видалення та збереження цілісності відбувається виключно через корінь `Deals`. Клієнт `Clients` не є частиною агрегату угоди і не видаляється при роботі з угодами.

2. **Агрегат «Товар/Послуга» (Product Aggregate) — у CatalogDb:**
   - **Корінь агрегату:** Таблиця `Product`.
   - **Внутрішні сутності:** `ProductDetail` (1:1, технічний опис, одиниця виміру, тривалість у хвилинах, ставка ПДВ) та `PriceHistory` (1:N, журнал діючих та архівних тарифів з інтервалами валідності).
   - **Правило інваріанта:** Будь-яка зміна базової ціни послуги атомарно закриває попередній інтервал у `PriceHistory` та відкриває новий запис.

3. **Агрегат «Активність» (Activity Aggregate) — у ActivitiesDb:**
   - **Корінь агрегату:** Документ у колекції `activities`.
   - **Внутрішні елементи:** Вбудований об'єкт автора `author`, масив вкладених коментарів `comments` та список пов'язаних продуктів `relatedProducts`.
   - **Гібридне кешування:** При додаванні активності її знімок (останні 5 записів) атомарно додається у вбудований масив `recentActivities` документа в `client_timelines`.
   - **Винесена підсистема:** Довгі гілки обговорень (`discussions` та `discussion_messages`) виносяться за посиланням (`discussionId`), запобігаючи неконтрольованому зростанню розміру документа активності понад 16 МБ.

## 4. Спільна мова (Ubiquitous Language)

- **Lead (Лід):** Початковий контакт, щойно зареєстрована потенційна угода з непідтвердженою кваліфікацією.
- **Qualified (Кваліфіковано):** Етап, коли менеджер підтвердив наявність бюджету, потреби клієнта та дедлайнів.
- **ProposalSent (КП надіслано):** Клієнту сформовано та відправлено комерційну пропозицію з попереднім набором послуг.
- **Negotiation (Переговори):** Обговорення деталей договору, узгодження знижок та фінального скоупу робіт.
- **Won (Виграно):** Успішно укладена угода (фінальний етап; вимагає обов'язкової наявності хоча б однієї послуги/товару з ненульовою сумою).
- **Lost (Програно):** Зрив угоди на будь-якому з відкритих етапів; вимагає обов'язкового зазначення причини (`LostReason`).
- **Price Snapshot (Знімок ціни):** Незмінна фіксація вартості послуги в `DealItems` на момент формування комерційної пропозиції.

## 5. Таблиця відповідності еталону (eShop vs CRM)

| Концепція еталону (інтернет-магазин eShop) | Відповідник у домені CRM для малого бізнесу | Обґрунтування відповідності |
| :--- | :--- | :--- |
| **Customer** (Покупець) | **Clients** (Клієнти / Контрагенти) | Юридичні особи та ФОП, з якими студія веде переговори та укладає договори. |
| **Order** (Замовлення) | **Deals** (Угоди) | Ключовий бізнес-процес монетизації: угода проходить стадії від першого контакту до оплати. |
| **OrderItem** (Позиція замовлення) | **DealItems** (Позиції угоди) | Послуги та цифрові товари зі знімками цін, узгоджені в комерційній пропозиції. |
| **OrderDetails** (Деталі доставки) | **DealDetails** (Деталі угоди) | Розширені метадані: джерело ліда, опис потреб, причина зриву угоди, очікувана дата закриття. |
| **OrderStatusHistory** (Історія статусів) | **DealStatusHistory** (Журнал воронки) | Хронологічний аудит руху угоди по етапах воронки продажів. |
| **Статуси замовлення:**<br>• Submitted<br>• AwaitingValidation<br>• StockConfirmed<br>• Paid<br>• Shipped<br>• Cancelled | **Етапи воронки продажів:**<br>• `Lead`<br>• `Qualified`<br>• `ProposalSent`<br>• `Negotiation`<br>• `Won`<br>• `Lost` | Повна бізнес-відповідність життєвого циклу:<br>• Початок: отримання ліда.<br>• Валідація: кваліфікація бюджету й термінів.<br>• Підтвердження: відправка КП клієнту.<br>• Оплата: фінальні переговори.<br>• Виконання: успішне закриття угоди (`Won`).<br>• Скасування: відмова клієнта (`Lost`) з фіксацією причини. |
| **Catalog** (Каталог товарів) | **CatalogDb** (Прайс-лист студії) | Сервіс обліку вартості розробки, дизайну, маркетингу, ліцензій та історії тарифів. |
| **Reviews** (Відгуки покупців) | **ActivitiesDb** (Комунікації та активності) | Неструктурована документна інформація: дзвінки, листи, зустрічі, обговорення. |
